# 重点

- **问题描述**：$n$ 个男性和 $n$ 个女性通过偏好列表进行匹配。
- **关键定义**：
    - **匹配 (Matching)**：一组有序对，每个成员最多出现在一个对中。
    - **完美匹配 (Perfect Matching)**：男女数量相等且都有唯一匹配的对象。
    - **不稳定性 (Instability Matching)**：存在一对未匹配的男女，彼此更喜欢对方而非当前匹配的伴侣。
    - **稳定匹配 (Stable Matching)**：完美匹配且不存在不稳定性。
- **Gale-Shapley算法：**
    - **步骤：**
        - 所有男性和女性初始为自由状态。
        - 自由男性向未拒绝过他的最高偏好女性求婚。
        - 女性接受求婚（若自由）或比较当前伴侣与新求婚者，选择更偏好者。
        - 重复直到所有男性匹配完成。
    - **基本性质：**
        - **终止性：最多 $n²$ 次求婚。**
        - **完美匹配：算法最终返回完美匹配。**
        - **稳定性：算法返回的匹配是稳定的。**
-  **Gale-Shapley (GS) 算法的核心性质**
	* **有效伴侣 (Valid partner)**：如果存在某一个稳定匹配方案使得男士 $m$ 和女士 $w$ 被配对，那么 $w$ 就是 $m$ 的有效伴侣。
	* **男士最优分配 (Man-optimal assignment)**：在稳定匹配中，每个男士都匹配到了他在所有可能的“有效伴侣”中最偏好的那一位。
	* **女士最劣分配 (Woman-pessimal assignment)**：在GS算法（男士主动求婚版本）得出的匹配中，每位女士匹配到的都是她所有“有效伴侣”中最差的那一位。
	* **弱帕累托最优 (Weak Pareto optimal)**：男士最优的稳定匹配是弱帕累托最优的，这意味着不存在任何其他的完美匹配（无论是否稳定）能让**所有**男士都获得严格更好的结果。
	* **防欺骗性 (Cheatproof)**：不存在任何机制既能保证产出稳定匹配，又能完全防止所有参与者作弊。但在GS算法下，男士没有说谎的动机，而某些女士在特定情况下可以通过提供虚假的偏好列表来使自己获益。
- **变体与扩展问题**
	   * **稳定室友问题 (Stable Roommate Problem)**：匹配不分为男女两方，而是 $2n$ 个人两两匹配互排偏好。这种情况下，**并不保证**一定存在稳定匹配。
	   * **住院医匹配 (Matching Residents to Hospitals)**：这是稳定匹配的一个扩展应用（NRMP），引入了“不可接受的参与者”、数量不均等以及“受限的一夫多妻制”（一个医院招收多名医生）等概念。此外，该模型下的**偏远医院定理 (Rural Hospital Theorem)** 指出，偏远（不受欢迎）的医院在任何稳定匹配中都会招收到完全相同的一批医生。

-   **关键的证明与证明技巧**：
	  Gale-Shapley 算法的证明几乎全部采用了**反证法 (Proof by Contradiction)** 这一证明技巧。以下是几个关键证明的思路：
	-    **算法的终止性**
		* **技巧**：组合分析与最坏情况计数。
		* **证明思路**：男士是按偏好降序依次求婚的，每经过一次 `while` 循环，就必然有一个男士向一个新女士求婚。由于 $n$ 个男士每个人最多向 $n$ 个女士求婚，因此整个系统最多只有 $n^2$ 种可能的求婚组合，算法必然在最多 $n^2$ 次迭代后终止。
	-   **匹配的完美性**
		* **技巧**：反证法 + 逻辑链推导。
		* **引理**：女士一旦被求婚就不会再变为单身。
		* **证明思路**：假设算法终止时，匹配不是完美的。也就是说，比如存在男士 Zeus 未被匹配。如果有人未被匹配，由于男女数量相等，必定也存在某个女士 Amy 未被匹配。根据算法特性，**女士一旦被求婚就不会再变为单身**，这意味着 Amy 从未被任何人求婚过。但 Zeus 既然最终单身，按照算法逻辑，他必然已经向他列表上的**所有人**（包括 Amy）都求过婚了，这与 Amy 从未被求婚产生矛盾。
	-   **匹配的稳定性**
		* **技巧**：反证法 + 分情况讨论。
		* **证明思路**：假设最后得出的 GS 匹配 $S^*$ 存在不稳定对 $A-Z$（即他们比当前的伴侣更偏好彼此）。
		  * **情况 1**：$Z$ 从未向 $A$ 求过婚。这说明 $Z$ 在求婚列表中轮到 $A$ 之前就已经得到了现在的伴侣，所以 $Z$ 相对 $A$ 更喜欢他在 $S^*$ 中的伴侣，因此 $A-Z$ 不可能是不稳定对。
		  * **情况 2**：$Z$ 曾向 $A$ 求过婚。由于最终两人没在一起，说明 $A$ （当时或后来）拒绝了 $Z$。而女士只会在遇到更好的追求者时才会拒绝别人，所以 $A$ 一定更喜欢她在 $S^*$ 中的伴侣，因此 $A-Z$ 也不是不稳定对。两者皆矛盾。
	-   **男士最优性**
		* **技巧**：反证法 + “第一个发生的事件”
		* **证明思路**：假设在 GS 匹配 $S^*$ 中，有些男士没有匹配到自己最好的有效伴侣。
		  * **定义极端情况**：令男士 $Y$ 为在算法执行过程中，**第一个**被其有效伴侣（设为 $A$）拒绝的男士。
		  * 因为 $A$ 是 $Y$ 的有效伴侣，必然存在某个合法的稳定匹配 $S$，在 $S$ 中 $A$ 和 $Y$ 匹配在了一起。
		  * 在 GS 算法中，既然 $A$ 拒绝了 $Y$，必定是因为她正和某个她更喜欢的男士 $Z$ 订婚（即 $A$ 喜欢 $Z$ 胜过 $Y$）。
		  * 回到匹配 $S$ 中，设 $Z$ 此时的伴侣是 $B$。因为 $Y$ 是“整个系统中**第一个**被有效伴侣拒绝的人”，所以在 $A$ 拒绝 $Y$ 的这一刻，$Z$ 还没有被任何有效伴侣拒绝过，这意味着 $A$ 必定排在 $B$ 的前面（即 $Z$ 喜欢 $A$ 胜过 $B$）。
			  * 具体地说，如果 $Z$ 喜欢 $B$ 胜过 $A$），那么在 $Z$ 向 $A$ 求婚之前，$Z$ 一定先被 $B$ 拒绝了，而没有 $Z$ 向 $A$ 求婚，$Y$ 还不至于被 $A$ 拒绝。
		  * 现在在稳定匹配 $S$ 中：$A$ 喜欢 $Z$ 胜过她的伴侣 $Y$；$Z$ 喜欢 $A$ 胜过他的伴侣 $B$。这使得 $A-Z$ 在 $S$ 中构成了“不稳定对”，这与 $S$ 是稳定匹配的假设矛盾。

# 设计算法时需要考虑的问题

Gale-Shapley (GS) 算法的核心逻辑是“提议-拒绝 (Propose-And-Reject)”：男士按照偏好降序向女士求婚，女士如果有更好的选择就“向上交易 (trade up)”，踢掉当前未婚夫而接受更好的男士。

在将直觉层面的算法转化为计算机能高效执行的代码时，重点需要考虑**如何将时间复杂度优化到 $O(n^2)$**。具体设计时需要考虑以下数据结构和细节：

1. **如何表示未匹配的男士？**
   * 需要维护一个空闲男士的集合，在设计上可以使用**队列 (Queue)** 或链表来存储自由男士，从而可以在 $O(1)$ 时间内取出一个可以发起求婚的男士。

2. **如何记录当前的匹配状态？**
   * 维护两个数组 `wife[m]` 和 `husband[w]`。初始值设为 0（代表未匹配），这样就可以在 $O(1)$ 时间内更新或查询任何人的配偶。

3. **男士如何高效地发起求婚？**
   * 为每个男士维护一个按偏好排序的女士数组。同时，维护一个指针/计数器数组 `count[m]`，记录男士 $m$ 已经求婚的次数。这样每次男士 $m$ 被弹出队列时，可以直接通过 `count[m]` 找到下一个该求婚的女士，单次求婚操作耗时 $O(1)$。

4. ==**女士如何高效地决定是接受还是拒绝？**==
   * 当男士 $m$ 向女士 $w$ 求婚时，女士 $w$ 需要判断她更喜欢当前的未婚夫 $m'$ 还是新的追求者 $m$。
   * 如果每次都遍历 $w$ 的偏好列表，单次查询将需要 $O(n)$，导致总复杂度退化为 $O(n^3)$。
   * **解决方案（空间换时间）**：通过 $O(n^2)$ 的预处理，为每个女士建立一个**逆序偏好列表 (Inverse preference list)** 数组 `inverse[pref[i]] = i`。这样查询“女士是否更喜欢 $m$ 胜过 $m'$”时，只需比较 `inverse[m] < inverse[m']`，将查询时间降至 $O(1)$。

# 作业

关于 GS 算法一共有两类问题：
1. 把问题划归为 GS 问题，并用 GS 算法求解，最后证明 GS 算法得到的匹配就是符合问题约束的匹配。
2. 为 GS 算法添加更多的限制（比如，部分配对是不允许的，比方说某医生少了某个证书，某个医院只招收拥有该证书的医生），或者允许 GS 问题的 Preference List 中出现平手，或者允许 Proposor 与 Proposee 数量不一致。 

## 第一类问题：

> 把问题划归为 G-S 算法。那么需要阐明：1. 谁是主动方（proposor），谁是接受方（proposee）；2. 根据现有规则为 proposor 与 proposee 设计一套 preference list 的规则。

典型问题：教材习题 6、7（这两题的套路一模一样）
### 如何把一个实际问题转为 G-S 问题？

-   **Step1**：问题中是否存在两类对象？且每个对象最终必须要匹配一个另一边对象，而且题目要求的是“是否存在一个符合条件的好匹配”
	-   比如，Problem2中，我们发现问题中有两个集合：船与港口，船一定与港口匹配，而且我们的目标是找到一个有效的 truncation 方案使得所有的港口不会有两艘船都同时访问。
-   **Step2**：如何定义谁是 Proposor？谁是 Proposee？如何为两个集合制定 Preference List？
	-   这里我们需要使用的是 Proposor 的 Proposor-optimal 以及 Proposee 的 Proposee-pessimal 性质（Proposor总是先访问 Preference list 上靠前的 Proposee，每一次访问的 Proposee 的评价都不断下降的，而 Proposee 的配对对象 Proposor 的评价总是不断提升的）。根据题意中的顺序，按照顺序或者逆序构造 Preference List。
	-   比如：Problem2中对于每艘船都有一个schedule，我们可以按照船访问港口的顺序构造 Preference List；而每个港口都会被船访问，所以我们也可以根据港口被船访问的顺序，为港口设计 Preference List。那么，船和港口谁是 Proposor 谁是 Proposee 呢？这我们注意到两个细节：对于每一艘港口，我们需要找到一个最晚访问它的船，满足，在其之后没有其他船访问它。那么对于港口而言，它所匹配到的船的时间是越来越玩的；题目里的schedule是按照船的口径给出的。所以，这里我们更倾向船作为 Proposor。那么 Preference List 的定义就很清楚了，对于每一艘船，schedule 上的港口越早访问 Preference List 排的越靠前；对于每一个港口，船越晚访问 Preference List 上排得越靠前。
-   **Step3**：证明 GS 算法得到的匹配一定是符合题意的。使用反证法，如果 GS 算法得到的匹配中存在不符合题意的情况，那么一定能推导出不稳定对。
-   **Step4**：证明算法的可终止性，就是 GS 算法的计算次数上限。
